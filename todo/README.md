# TODO system: format spec

The `todo/` tree is the live execution plan for building the project. Markdown is canonical; `build/todo-cache.json` is a derived, gitignored projection. The one committed derived artefact is [`implementation-plan.md`](./implementation-plan.md) (or the path a project names as `layout.plan` in `todo/plan.json`), generated from the sections and never edited by hand.

One rule governs everything below: **a TODO section must be implementable by someone with zero conversation context.** A fresh session starts with none. If a section only makes sense to someone who was in the room, it is not done.

This system is seeded by Conclave-SDK in its clean strict form: one validator that refuses malformed work, a generated plan, and stamps backed by review receipts. The governing product documents stay where they are: architecture and milestones in `docs/plans/`, the interface in `design/SPEC.md`. TODO files execute those documents; they do not restate them.

## Tree shape

```text
todo/
├── README.md               this file
├── TODO-00-INDEX.md        root index: domain order + active work
├── implementation-plan.md  generated by plan --sync; never edited by hand (or at layout.plan)
├── plan.json               the plan's title, acceptance bar and phase names
├── findings.md             defects noticed while doing something else (file:line, unscheduled)
├── templates/              TODO-template.md (same file the create-todo skill carries)
├── 00-workspace/
│   ├── INDEX.md            domain index: every TODO in this domain
│   ├── TODO-01-<short-name>.md
│   └── TODO-02-<short-name>.md
└── 01-engine/
```

Domains are flat-numbered in allocation order and map to the foundation plan's milestones. Numbers are stable addresses: a new domain appends after the last one, because `DNN` cross-references encode them. Execution order lives in the dependency graph, not in the numbering.

Naming: `TODO-NN-short-name.md`, where `NN` is the next free number within that domain. Numbers are never reused. Renaming a file is safe: the stable `id` in frontmatter is what file-level references resolve against.

## Frontmatter

Every TODO file opens with YAML frontmatter, one scalar per line. Five required fields, four optional. That is the whole schema: resist adding more.

```yaml
---
schema_version: 1
id: example-runtime                # stable, kebab-case, globally unique, survives renames
domain: 01-engine                  # must match the containing directory
status: active                     # draft | active | blocked | done | superseded
title: "TODO-01 -- Example Runtime"
depends_on: ["repo-and-build"]     # optional: TODO ids that must fully ship first
frozen: true                       # optional: touches the frozen thread-safety contract
track: M1                          # optional: milestone reference
superseded_by: other-todo-id       # required with status: superseded
---
```

`id` rules: lowercase `a-z0-9-`, 2 to 60 chars, starts with a letter, no trailing dash. It must not change once other files point at it. Only `active` files produce ready sections. `done` is true exactly when every section is stamped (the last stamp sets it). A `superseded` file must name where its work went.

## File anatomy

In order: frontmatter, `# TODO-NN -- Title`, `> **Goal:**`, `> **Current state:**` (measured, dated, real paths), `## Inputs`, `## Outcome` (with the Adjacency line), `## Implementation Order`, the numbered sections `## 1.` to `## N.` in ascending order, and `## Verification` last. New sections go in numerical position, never after `## Verification`.

### The Implementation Order table is the dependency graph

Every `## N.` body section has exactly one row (`Order`, `§N`, `Deliverable`, `Depends On`, `[ ]`), and every row has exactly one body section. Keep every section heading (`## N. <Title>`) and its `Deliverable` cell (plus `Scope` cells in index tables) to a concise noun phrase of at most 88 characters (`deliverable_len`) so raw Markdown table rows stay under 140 characters (with description cells within the Deliverable cap) and never wrap in raw `.md` view; put file paths, symbol lists, and flags in the section body and checklist. The validator enforces both directions, refuses `Deliverable` or section titles over 88 characters (`deliverable_len`), refuses cycles, refuses a prerequisite in a later phase than its consumer, and refuses a ticked row without its stamp. A file holds at most 55 sections (`sections_per_file`): past that, the next work opens a new file in the same domain, split by subject. Section numbers are permanent addresses and are never renumbered.

The caps named in parentheses are defaults. A project sets its own in `todo/plan.json` as `caps`, an object with any of `sections_per_file` (1 to 200), `items_per_section` (2 to 200, since a section holds a work item and its Commit), `deliverable_len` (20 to 200) and `table_row` (60 to 400), each a whole number; a cap left out keeps its default. `table_row` is the widest row of the generated plan's tables, which pad every row to the widest Deliverable, so a longer `deliverable_len` needs a longer `table_row`. The review caps belong to the reviewer pin (`.conclave/reviewers.toml`), not `plan.json`. The generated plan is `todo/implementation-plan.md` unless `layout.plan` names another: a `.md` file under the same naming rules, never `todo/plan.json`, `todo/README.md`, a file in a `todo/NN-domain/` folder or in the receipts folder, and never an existing file without the plan's generated notice line, so `plan --sync` cannot overwrite a document the plan does not own. `python scripts/todo-graph.py plan-path` prints it, and the pre-commit hook (`scripts/hooks/pre-commit`) watches it: git runs the hook once `core.hooksPath` is `scripts/hooks`, which the kit's install sets where nothing else owns the repository's hooks, which the kit's doctor reports as `pre-commit-hook`, and which a fresh clone sets with `git config core.hooksPath scripts/hooks`. Receipts, findings files and `legacy-receipts.json` live in one folder, `docs/reviews` by default; a project that keeps them elsewhere names it in `todo/plan.json` as `layout`, an object whose `receipts` is the folder: folder names of letters, digits, `_`, `.` and `-` (a leading dot too, as in `.claude/overnight/reviews`, but never `.` or `..`) separated by `/`, inside the repository and reached through no link, since a findings file is never read through one. The pre-commit hook watches the folder the staged `todo/plan.json` names as well as the working one, so an unstaged layout change cannot move it off the folder being committed. The root index (`todo/TODO-00-INDEX.md`) lists every TODO file unless `layout.root_index` says `domains`, when it lists each domain's `INDEX.md` instead and only the domain index lists the files; `files` is the default. The graph, the stamp, the pre-commit hook (through `python scripts/todo-graph.py receipts`), `review-dispatch.py` and `review-prompt.py` all read it, and the skills write it as `<receipts>`.

### Cross-reference notation

| Form | Means | Example |
| ---- | ----- | ------- |
| `§N` | Section N of this same file | `§3` |
| `TNN §N` | TODO-NN in the same domain, section N | `T02 §1` |
| `DNN TNN §N` | Domain NN, TODO-NN, section N | `D03 T01 §4` |

Never a bare number, and never a cross-TODO reference without a section. Cross-references in `-> XREF:` lines are bidirectional at file level: if this file points at `D03 T01 §4`, that TODO file must point back at a section in this file. The validator refuses one-sided XREFs and XREFs that name no real section.

### What every section declares

- `**Phase:**` from the project's phase list: by default 0 to 7 or 99 (Manual, operator only). The phase drives plan ordering (numeric, with 99 last); changing one is a scope decision. The project names its phases, the plan's title and its acceptance bar in `todo/plan.json` (`{"title": ..., "acceptance": ... or null, "phases": {"0": "<name>", ...}, "phase_list": [0, 1, ...]}`), where the optional `phase_list` sets the phase numbers a section may use (distinct whole numbers from 0 to 999; without it, 0 to 7 and 99); `validate` and `plan` refuse unknown keys, a malformed `phase_list`, and a phase number or phase name outside it.
- `**Needs:**` `none` or a comma-separated list from: `windows-host`, `arm64-host`, `display-session`, `office`, `libreoffice`, `store-account`, `attended`, `owner-decision`, `third-party`, `operator`. `owner-decision`, `third-party` and `operator` hold the section out of `query ready` until the answer is recorded and the Need is removed. Unattended runs never take an `attended`, `store-account` or `operator` section. A runner asks `query ready --have auto` and `resolve --have auto`: a row with a Need this session does not meet (other than a waiting one, which holds it anyway) is held, and `resolve` names it in `missing_needs`. The session's set is the kit's own probes (`windows-host`, `arm64-host`, `display-session`, `libreoffice`, `office`), the project's `probes` in `todo/plan.json` (an object from a Need in `needs` to the command that proves it, an argument list run with no shell and a 10-second timeout, met when it exits 0) and the Needs the session declares in `CONCLAVE_HAVE` (comma-separated, for what no program can see, such as `attended`); `python scripts/todo-graph.py detect` prints it, and `--have <need,...>` names a set outright. These are the defaults: a project with Needs of its own lists them in `todo/plan.json` as `needs` (distinct names matching `[a-z0-9][a-z0-9-]*`; `none` is reserved, since `**Needs:** none` means no Need), and the ones a person must answer as `waiting`, which must all be in `needs`. Without `waiting`, the waiting Needs are the three above among those `needs` lists. A waiting Need holds a section out of `query ready` and refuses its stamp, and a stamped section may not carry one, so adding a stamped section's Need to `waiting` later is refused until the section is reopened.
- `**Surface:**` `yes` or `no`. A `yes` section builds or changes a user-facing surface and also carries four lines: `**Fidelity:**`, `**Job:**`, `**Treatment:**`, and `**Chrome:**`.
- `**Freeze check:**` in every section of a `frozen: true` file, and nowhere else.
- `**Build order:**` numbered steps, each naming a path, class, command or artifact in backticks and an observable `Done when:`.
- A checklist of 2 to 30 items (`items_per_section`): micro-steps, then `- [ ] Commit: <message>` last. One item is one buildable step: one action, a named path or symbol in backticks, a `Done when:` observable end state in the same bullet, a `Cheaper substitute:` on UI and write items, and a source citation when behavior is copied from the SPEC, the foundation plan, or upstream specifications.
- `**Test checkpoint:**` a runnable command in backticks with its expected result. It must be able to fail.

Do not rewrite a `[x]` section's checklist: that is the contract its stamp covers. New granularity on shipped work is a new section.

### Micro/small items and 100% complete development plan

- **Small, single-responsibility sections:** Never bundle multiple subsystems, dialogs, or workflows into one coarse umbrella section. Split work into small, single-responsibility sections that each deliver one coherent capability, with explicit `Depends On` edges in the Implementation Order table.
- **Short table descriptions (`<= 88` chars, or `deliverable_len`):** Every `Deliverable` cell and `## N. <Title>` heading is a short noun phrase (`<= 88` chars or the project's `deliverable_len`, enforced by `validate`) so raw `.md` table rows in `TODO-*.md` and `todo/implementation-plan.md` (or `layout.plan`) never wrap in the editor.
- **Granular micro-step checklist items (five-part rule):** Never write a 1-bullet or 2-bullet summary checkbox for an entire subsystem. Decompose every section into individual micro-step checkboxes (typically 4 to 15 micro-steps per section, max 30 or the project's `items_per_section`). Every non-`Commit:` item carries: (1) one action (never "do X and then Y"), (2) a concrete path, symbol, or command in backticks, (3) `Done when:` observable end state in the same bullet, (4) `Cheaper substitute:` on UI and write items so the checkpoint and reviewer fail on shortcuts or wrong-layer edits, and (5) a source citation when copying behavior.
- **100% complete development plan:** Running `process-plan` to completion must leave a 100% complete, shippable product. Every milestone commitment in the foundation plan and every screen, dialog, control, command, setting, error/refusal path, undo/reverse operation, and persistence read-back in `design/SPEC.md` is owned by a concrete section and micro-step. Never cap operator-requested planning and never silently drop scope.
- **Surface completeness (`Surface: yes`):** Every control, menu item, dialog, and state on the SPEC surface is either working (proven on the rendered surface with real data and read-back) or deferred to a named, resolving section (`-> XREF: DNN TNN §N`). A disabled or stubbed control with no resolving owner section refuses validation and review.
- **Logical step commits:** Commits follow logical steps within a section; a section may land in one or more step commits, and review fix-loop commits append to the candidate range without amending.

### Brownfield code and incomplete TODO trees

When adopting or grooming this system on a repository where code is already partially implemented or the `todo/` tree is incomplete:

- **A project that adopts the kit with stamps of its own** runs `python scripts/todo-graph.py adopt-stamps [--phase-map <file>]` once: each section whose body carries a `> **Verified:**` line, in whatever format the project used, is frozen under `adopted` in `<receipts>/legacy-receipts.json` with its full commit (the first commit name in that line, resolved by git and on the branch), its phase (the phase map by section, then by file, then the body's own `**Phase:**`) and the digests of its body and of the receipt its `Review:` line names, under an `adoption` marker that refuses a second adoption. While both digests hold, the validator takes the section as stamped and checks only the graph (dependencies, phase order, XREFs, indexes); an edit to either refuses until `unstamp` reopens it, after which it is open work in the kit's format and is stamped the kit's way.
- **Already-stamped `[x]` sections are never rewritten:** Their checklist is the historical contract covered by their receipt. If a `[x]` section was coarse or left gaps, keep it untouched and file the missing work as a new `## N.` section in numerical order with `-> XREF:` back to the original section. If a `[x]` section's `Test checkpoint` no longer passes, `review-todo-section` in audit stance flips it back to `[ ]` with a dated regression note.
- **Open `[ ]` micro-steps already implemented in code:** During `groom-plan` or `process-todo-section` Step 2/3, verify the existing code against the micro-step's `Done when:` and `Cheaper substitute:`. If 100% satisfied, tick `[x]` with the `file:line` and commit SHA that shipped it. If only partially implemented (for example, happy path exists but refusal path, token binding, or test is missing), leave it `[ ]`, update `> **Current state:**` to name what exists, and decompose the remaining work into concrete micro-steps.
- **Open `[ ]` section already 100% implemented in code:** Do not churn working code just to manufacture a diff. Verify every micro-step's `Done when:`, add any missing falsifiable test if the checkpoint cannot fail, run the `Test checkpoint` for real, commit the ticked checklist and verification evidence, and run `review-todo-section` plus `stamp` against the implementing or verification commit SHA.
- **Features already in the codebase with no TODO file:** Features that are already 100% complete and tested in the baseline codebase are recorded in `> **Current state:**` of the relevant domain's TODO file; features that are incomplete, untested, or stubbed get small single-responsibility sections and five-part micro-steps for the remaining work so (`baseline code` + `open plan`) equals a 100% complete product.

### Adjacency: the surfaces a file owes beyond its record

`## Outcome` carries one executable `**Adjacency:**` line. Write every key exactly once, separated by semicolons: `key=applicable`, `key=applicable @ DNN TNN §N` for an explicit owner, or `key=not-applicable (reason)`. A narrow non-feature file may declare `all=not-applicable (reason)`. The nine keys: `list` (find a record without its identifier), `document` (what a user carries, sends, prints or files), `settings` (every tunable, with a named consumer), `reporting` (summaries and exports over the domain's data), `notifications` (lifecycle notices with recipient rules), `permissions` (refusals exercised, both ways), `audit` (who changed what, and the diagnostic trail), `exchange` (import and export), `reverse` (the undo of every create: cancel, reopen, revert). "Not applicable" is a declaration with a reason, not silence. Owner references must resolve; `python scripts/todo-graph.py query adjacency` prints every declaration. An `**Adjacency rationale:**` paragraph under the line records the substantive decisions for human review.

## Stamps and receipts

A section closes only through `stamp`, after the review passes the project's pin (`.conclave/reviewers.toml`) schedules. Under a three-pass pin (`[schedule] policy = "three-pass"`, what a new install starts on) those are a plan review, one round, a completion review and reconciliations after gaps:

```powershell
python scripts/todo-graph.py stamp 'D01 T01 §1' --sha <full 40-char tip commit> --plan docs/reviews/01-engine/D01-T01-s1.md --completion 'docs/reviews/01-engine/D01-T01-s1.md:<complete|reconciled|filed>' --review '<N>:docs/reviews/01-engine/D01-T01-s1.md:<clean|fixed>' --check '<command> -> <quoted result>'
```

`<N>` is the number of the one round that returned a review: 1, or the `## Round N` the dispatcher recorded it under when an earlier attempt returned none.

A stamp writes the receipt, then the TODO file, then the plan. If it was cut short between those writes (the process was killed), run the same `stamp` command again: it replaces the leftover receipt, stamps the TODO file and regenerates a stale plan. A request that differs (another commit, review, plan review or completion review) is refused, naming what differs, and writes nothing.

Under a rotation pin (no `policy` key) the completion review comes before the rounds, there is one `--review` per round, and the completion verdicts are `complete`, `completed` and `filed`. `review-todo-section` has the whole flow for both.

## Commands

```powershell
python scripts/todo-graph.py validate            # structure + graph integrity; exits 2 with the reason on any fault
python scripts/todo-graph.py build               # parse todo/ -> build/todo-cache.json
python scripts/todo-graph.py render              # mermaid dependency graph
python scripts/todo-graph.py validate --all      # every fault at once, one line each (exit 2); plain validate stops at the first
python scripts/todo-graph.py plan --sync         # regenerate the plan (layout.plan) after any edit
python scripts/todo-graph.py plan --check        # fail if the generated plan is stale (CI runs this)
python scripts/todo-graph.py query ready         # sections that can run now (also: blocked, stats, deferred, adjacency, plan, rounds)
python scripts/todo-graph.py query frozen        # each frozen file's Freeze-check coverage, read from the tree alone
python scripts/todo-graph.py query sequence      # the longest open chain, and the sections each stamped one filed
python scripts/todo-graph.py detect               # the Needs this session meets (probes and CONCLAVE_HAVE)
python scripts/todo-graph.py query ready --have auto  # only the rows whose Needs this session meets (resolve takes it too)
python scripts/todo-graph.py resolve 'D01 T01 §1'  # 0 ready, 1 no such section, 2 no reference, 3 verified, 4 waiting
python scripts/todo-graph.py classify 'D01 T01 §1' 'D02 T01 §1'   # dispositions as JSON
python scripts/todo-graph.py stamp 'D01 T01 §1' --sha <commit> --plan <report> --completion '<report>:complete' --review '1:<report>:clean' --check '<cmd> -> <result>'
python -m unittest tests.scripts.test_todo_graph   # the tooling's own tests
```

## Skills

| Skill | Use |
| ----- | --- |
| `add-todo` | Route new work to the right domain, file, and section. |
| `create-todo` | Author a new TODO file, wire XREFs, and update indexes. |
| `groom-plan` | Harden sequence, drift, gaps, and micro-step granularity. |
| `process-todo-section` | Fact-check, repair drift, and ship exactly one section. |
| `review-todo-section` | Run review lenses and write the stamp via `stamp`. |
| `process-todo-file` | Run loose-end sweep and close an all-`[x]` file. |
| `process-phase` | Repair, gap-audit, and run a phase to 100% or park it. |
| `process-plan` | Front door for `implementation-plan.md` (or `layout.plan`); chains phases. |

## Rules for every file

- One line per paragraph and per list item in Markdown prose; no em dashes or en dashes in new text; keep Markdown table description cells at or under 88 characters (or the project's `deliverable_len`) so they do not wrap in raw `.md` view.
- A defect noticed outside the current work is filed in `todo/findings.md` with `file:line`, not fixed on the side inside someone else's commit; scheduling it means writing a section through `add-todo`.
- Questions that need a person are not TODO rows without a Need: the section names `owner-decision` or `third-party` and records the answer before the Need is removed.
